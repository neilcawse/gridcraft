## Workbook window settings

GridCraft keeps one modelled workbook window. On XLSX import it selects the first visible
`workbookView` (omitted `visibility` means visible), or the first view when none is visible.
The active tab and display options come from that same view and survive the next save.
GridCraft normalizes `tabRatio` to 0–1000 on import and export; malformed or overflowing
unsigned-integer text uses the default 600. The valid endpoints 0 and 1000 survive, and
600 plus the default shown flags stay omitted from output. Synthetic regressions in
`crates/xlsx/src/tests/roundtrip.rs` cover each attribute independently, selection, fallback
and round trips (#3057). Engine regressions exercise real sheet deletion and reordering
commands and check that the saved active tab identifies the current sheet after reopening,
with the workbook display options preserved.
The format's [workbook-view defaults](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.workbookview?view=openxml-3.0.1)
include visible windows and a tab ratio of 600. UI controls and rendering of these settings
remain separate #3057 work.

`firstSheet` records the leftmost visible tab, independently of `activeTab`. It is not modelled
by this branch. Supporting it needs its own view state and sheet-edit handling, tracked in
#2264; these regressions cover the active tab and existing display fields without introducing
that separate feature.

## Workbook formats

XLSX column declarations are limited to 1,000,000 expanded column assignments per worksheet,
including repeated overlaps across `<cols>` blocks. Spans are clipped to the grid and records
that would be skipped as defaults are excluded before charging the limit. Excess work returns
the existing file-too-large error; accepted overlaps retain their existing last-wins behavior
(#1022).

Ink created with Draw is written as standard, unfilled DrawingML polylines, without visible point
captions or private metadata. Supported numeric polylines reopen as editable ink, retaining points,
colour, integer width and anchor. Curves, filled paths, transforms and unsupported line styles are
not interpreted as ink. This does not implement Office InkML or fix inserted icons (#551).
Command and package tests cover repeated saves and unrelated cell edits; external Excel rendering
and repair-free opening remain unverified.

Dynamic-array formulas keep their mark on save. A formula read with dynamic-array cell metadata
(`cm`, the `XLDAPR` record in `xl/metadata.xml`) is written back with it, together with the
metadata part, even when it returns one value and GridCraft's own shape analysis would not need
array evaluation. Dropping the mark turned such formulas into legacy ones, which Excel evaluates
with implicit intersection: `SUMPRODUCT(IFERROR(B1:B3/C1:C3,0))` recalculated to a different
value in Excel. Moving the formula, inserting or deleting rows and columns, and renaming sheets or
names keep the mark; retyping the formula drops it, and the writer then decides from the
formula's shape. Rich-value metadata other than cell pictures and errors (data types) is still
dropped. Excel saves `#SPILL!` and `#CALC!` as `t="e"` cells holding `#VALUE!` with a `vm` that
points at an `_error` rich value (`xl/richData`, `errorType` 8 and 13); XLSX open reads such a cell
as the error it shows, on formula cells and on constant ones (`ERROR.TYPE` of one is 9 or 14).

Formulas from Google Sheets' XLSX export open as the formulas written in Google Sheets (#2871).
Google writes a formula that uses a function it thinks Excel lacks as
`IFERROR(__xludf.DUMMYFUNCTION("<formula, quotes doubled>"),<cached value>)`, which Excel shows
as the cached fallback. GridCraft recognises exactly that shape (any case, with or without
`_xlfn.` on `IFERROR`), in plain, shared and `t="array"` cell formulas, as the whole formula or
inside a larger one (`=1+IFERROR(__xludf.DUMMYFUNCTION("A1+2"),5)` opens as `=1+(A1+2)`), and
reads the formula inside when it parses and GridCraft calculates every function it calls. The
cell keeps the file's cached value. A Google-only function (`GOOGLETRANSLATE`, `QUERY`,
`ARRAYFORMULA`…) keeps the wrapper, so the cell shows the cached value as in Excel rather than
`#NAME?`; so does inner text that doesn't parse, is longer than 8,192 characters or would nest
past the parser's limit, and a wrapper inside the text. **Saving writes the real formula** (with
`_xlfn.` prefixes, e.g. `_xlfn._xlws.FILTER`), not the wrapper: this is what Excel does with the
`_xlfn.` functions it knows (`google_sheets_dummy.rs`, `fmla.rs`, engine `io/tests.rs`).

## Python cells

| Where | GridCraft | Notes |
|---|---|---|
| `.xlsx` | read and write | Written as [MS-XLSX] 2.3.10 specifies: the cell's formula is `_xlfn._xlws.PY(i,n)`, where `i` is the index of the cell's script in the workbook's Python part (`xl/python.xml`, `application/vnd.ms-excel.python+xml`) and `n` the return type, 0 for an Excel value or 1 for a Python object, with the cached value. The code keeps its `xl()` references as text, so the formula has no further arguments. A spilling result is written as a dynamic array with its spilled values cached. Read back when the formula calls the function by the name the file format gives it, `_xlfn._xlws.PY` ([MS-XLSX] 2.2.2 `solo-function`, in any letter case): an index names a script of the Python part, whose `%Px%` references become the text of the formula's argument `x`, and the older form with the code in string literals, `_xlfn._xlws.PY("…"&"…",n)`, still reads. A call to plain `PY`, to `_xlfn.PY` or to `_xludf.PY` is a user-defined function of the file ([MS-XLSX] 2.2.2 `user-defined-function-call`) and stays a formula. So workbooks laid out as the format specifies open with Python cells, their cached values and spills. Python errors are cached as `#VALUE!`, as Excel caches `#SPILL!` and `#CALC!` |
| `.xls`, `.xlsb`, `.ods`, CSV, HTML, SYLK | read | No Python cells: a format that doesn't declare them has none, so a `PY(…)` call read from it stays what the file says. In `.xls` that is a call to a user-defined function named PY ([MS-XLS] 2.5.198.63 PtgFuncVar with iftab 255 over a PtgName of a function Lbl, 2.4.150): its formula, array and cached result are kept, and a save to `.xlsx` writes that formula back instead of code in a Python part. The `.xlsb` and `.ods` imports keep values only for functions GridCraft doesn't have, so a Python result there comes in as its cached value |
| GridCraft JSON | read and write | The whole Python cell: code, return type, the last result and the exact error |
| Limits on open | — | Code that doesn't fit Excel's 8,192-character formula as `PY("…",n)` keeps only its cached value, with a warning, and so does a formula naming a script the Python part doesn't hold. The Python part is read up to 64 MB and 1,000,000 scripts, and the cells take at most 64 MB of code from it in all (several formulas can name one script). A kept result that is not a well-formed array of at most 1,000,000 cells is dropped, a spill range larger than that is ignored, and results are rebuilt for at most 4,000,000 cells over the workbook. A Python cell that keeps only its value (code too long or not in the part, a damaged part, a dropped result, a result past that budget) keeps the values it spilled as plain values, without overwriting a cell's own content or format. Opening runs nothing |
| Not kept | — | Python object results stored as rich values (Excel's `richData` parts) come in as their cached values. The Python part's environment definition (its id and initialization code) is not read, and a save writes none |

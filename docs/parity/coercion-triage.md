# Value coercion and Lotus transition evaluation

Evidence below names public corpus files only; formulas, cell contents and sheet names from those files are paraphrased, not quoted.

## Confirmed causes

- **Transition arithmetic is a worksheet setting.** The setting is `sheetPr/@transitionEvaluation` (ECMA-376 `CT_SheetPr`, default false). On flagged sheets, cached results show arithmetic operators reading a text operand as zero where an ordinary sheet gives `#VALUE!`: a percentage-change formula over a literal text cell in `0f7ddb20-e7ec-43fa-a185-d2ed72cc7ef0.xlsx`, a `SUM` minus one of its own text inputs in `97542774-c5ab-416c-973e-793aaa388405.xlsx`, and, in `December.xlsx`, a number plus a text literal divided by a number, so the rule covers text literals as well as references. An unflagged sheet in `3021382e-04e6-4475-9bf4-437d6a544e0a.xlsx` only sees a flagged sheet's results through `SUM` and `ROUND`: the setting belongs to the sheet that holds the formula, not to the sheets it reads. GridCraft applies it to the formula's own sheet, also while it evaluates a defined name scoped to another sheet. This agrees with [Excel's transition formula evaluation rules](https://documentation.help/MS-Office-Excel-2003/xlrefRulesUsedInCalculatingLotus123Formulas1.htm) ("cells that contain text are considered to have a value of 0"). On the flagged sheets of the public XLSX corpus, no formula built only from references, numbers and arithmetic operators reads a text that looks like a number. Reading numeric text as zero therefore rests on that documentation alone. Worksheet functions keep their ordinary coercion.
- **Transition comparisons are distinct from ordinary comparisons.** On a flagged sheet of `SSCOTT8-22-00.xlsx`, an `IF` whose test compares a blank cell with a single-space text takes its true branch. On a flagged companion sheet, an `IF` that compares a formula returning `""` with 0 also takes its true branch. Only these two pairs change: a blank against `" "`, and empty text against a number (read as a blank). They do not imply that a space, the empty string and a blank are interchangeable on ordinary sheets or outside comparisons.
- **Unary plus does not convert to a number.** The Excel-saved `MINUS_MINUS.xlsx` caches unary plus of the Boolean literal as a Boolean, and `TYPE` of unary plus over a numeric text literal as 2 (text). Other caches keep referenced Booleans. On flagged sheets of the public XLSX corpus, all 31 formulas that are unary plus of one reference to text cache the text itself: unary plus is not arithmetic, even on transition sheets. In the public `Time.xls`, an `IF` that tests whether unary plus of a genuinely blank cell equals `""` takes its true branch with transition evaluation off, so the intermediate blank survives. A blank that is a formula's final result still shows as zero. No cache establishes whether reference-taking functions (`ROW`, `ISREF`) see a reference through unary plus, or whether functions that count blanks see blanks inside unary plus of a range. GridCraft gives them values.

## Residuals and migration

- The selected public BIFF examples have 206 mismatched formula cells on transition-enabled sheets in four `.xls` workbooks. This counts the discrepancies on those sheets. It does not claim that the flag causes all 206. In `SCD-G1.XLS` and `OPEC2.XLS`, additions over text operands cache what reading the text as zero gives. The adapter cannot infer the setting from formulas or cached results. A future `craft-xls` API should expose `Sheet::transition_evaluation: bool` (default false), populated from `fAltExprEval` in the [WsBool record](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xls/ccbd73f9-ff1d-4069-be31-13d16c074ec4). The GridCraft adapter can then copy it to the worksheet model and keep it on XLSX export.
- XLSB has the same flag (`fAltExprEval` in [`BrtWsProp`](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xlsb/4f648423-1efd-489c-90eb-ca410b8c5a12)). The `craft-xlsx` package reader owns this record and would need to pass the flag through to GridCraft. No selected XLSB mismatch was attributed to this flag.
- The comparison rules above do not change the result type of logical expressions. The documented 0/1 display in transition mode does not establish the internal value type, and the inspected flagged sheets have no standalone logical-result caches that tell the two apart.
- Two legacy formulas in one workbook cache `N` of an entirely blank cross-sheet row range as zero. Taking the first cell explains this, but so do other ways of handling blank input. `N` already takes the first cell of a reference in the function evaluator, and the legacy XLSX importer has a separate implicit-intersection rule. That rule should stay as it is until there is more evidence, especially for nonblank ranges and computed arrays.
- Fifteen public query workbooks use manual calc and cache a bare legacy `Concat` call over a range of row numbers as `#VALUE!`. These caches do not establish how modern [CONCAT](https://support.microsoft.com/en-us/office/concat-function-9b1a9a3f-94ff-41af-9736-694cbd6b4ca2) behaves, since it accepts ranges. The missing future-function prefix, the old formulas and manual calc all point to legacy function resolution or stale caches. Text-function discrepancies that depend on these cells should not drive changes to `CONCAT`, `LEFT`, `LEN`, `TRIM` or `&`.

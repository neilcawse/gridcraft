# Value coercion and Lotus transition evaluation

Evidence below names public corpus files only; formulas, cell contents and sheet names from those files are paraphrased, not quoted.

## Confirmed causes

- **Transition arithmetic is a worksheet setting.** The setting is `sheetPr/@transitionEvaluation` (ECMA-376 `CT_SheetPr`, default false). On flagged sheets, public caches show arithmetic operators reading a text operand as zero where an ordinary sheet gives `#VALUE!`: a percentage-change formula over a literal text cell in `0f7ddb20-e7ec-43fa-a185-d2ed72cc7ef0.xlsx`, a `SUM` minus one of its own text inputs in `97542774-c5ab-416c-973e-793aaa388405.xlsx`, and a number plus a text literal divided by a number in `December.xlsx`. The synthetic probe also confirms that the numeric text `"1"` reads as zero for arithmetic. The setting belongs to the formula's worksheet, not the sheets it reads, even when a formula evaluates a defined name scoped to another sheet. This agrees with [Excel's transition formula evaluation rules](https://documentation.help/MS-Office-Excel-2003/xlrefRulesUsedInCalculatingLotus123Formulas1.htm) ("cells that contain text are considered to have a value of 0").
- **Transition comparisons use numeric coercion unless both operands are text.** For all six operators, blanks and text compare as zero against non-text operands, Booleans compare as 0 or 1, and numbers keep their values. Two text operands (including empty text and spaces) keep ordinary text ordering. Comparisons still return Booleans and propagate errors. This replaces the narrower rule inferred from the `SSCOTT8-22-00.xlsx` equality caches.
- **Scalar `&` rejects a genuine blank on transition sheets.** The original probe measured `"x"&blank_cell`, including inside a selected `IF` branch. The follow-up measured `""&blank_cell`, `blank_cell&""`, `blank_cell&blank_cell`, `1&blank_cell`, and blanks returned by `INDEX` and `IF`: all return `#VALUE!` on transition sheets. Empty text is not a genuine blank (`"x"&""` still returns `"x"`). Boolean and array concatenation were not separately measured; the array path is unchanged.
- **Function rules depend on argument form.** On transition sheets, `AVERAGE` counts text literals as zero, including numeric text, nonnumeric text and `""`; text and blank references are still ignored and `TRUE` still counts as 1. Computed text and other aggregates such as `SUM` and `AVERAGEA` were not measured for this coercion and retain their existing handling. A plain text criterion under a named database field matches exactly rather than by prefix (measured with `DCOUNTA`); explicit operators, wildcards and computed criteria retain their existing treatment. `DATEVALUE` returns non-text scalar arguments numerically on transition sheets: numbers are unchanged (including negative, fractional and out-of-range values), `TRUE` becomes 1 and a blank becomes 0. This holds for literals, references and arithmetic results. Text still parses as a date on both sheets, and numeric text such as `"5"` returns `#VALUE!`. Array arguments were not measured.
- **`AGGREGATE` distinguishes references from array values on both sheets.** Codes 1–13 accept references and scalars, not array values: the original probe measured filtered division, and the follow-up found `#VALUE!` for every code 1–13 over `{1,2,3}`, for a name holding that constant, and for a reference followed by a constant array. Code 14 still accepts the constant, and eligible array-form filtered divisions keep their bounded-range shortcut. [Microsoft's `AGGREGATE` documentation](https://support.microsoft.com/en-us/excel/functions/aggregate-function) says 3-D references give `#VALUE!`; the probes did not measure that form and GridCraft still aggregates them.
  SpreadsheetBench's public `1_58221_answer.xlsx` independently caches a numeric result for code 15 over a same-shaped range divided by a text-equality mask, the optimized shape.
- **3-D references in arithmetic are not 3-D references in `SUM`.** In the follow-up, `First:Last!A1+0` returns `#REF!` on both sheet types, while `SUM(First:Last!A1)` returns 5 on both. GridCraft rejects written multi-sheet spans used as operands of binary arithmetic without changing reference consumers. Other operators and indirect forms (such as a name that resolves to a span) were not measured.

- **Unary plus does not convert to a number.** The Excel-saved `MINUS_MINUS.xlsx` caches unary plus of the Boolean literal as a Boolean, and `TYPE` of unary plus over a numeric text literal as 2 (text). Other caches keep referenced Booleans. All 31 inspected formulas applying unary plus to a single text-valued reference on flagged XLSX sheets cache the text itself: unary plus is not arithmetic, even on transition sheets. In the public `Time.xls`, an `IF` that tests whether unary plus of a genuinely blank cell equals `""` takes its true branch with transition evaluation off, so the intermediate blank survives. A blank that is a formula's final result still shows as zero. No cache establishes whether reference-taking functions (`ROW`, `ISREF`) see a reference through unary plus, or whether functions that count blanks see blanks inside unary plus of a range. GridCraft gives them values.

Follow-up evidence: Excel for Mac 16.115.2, synthetic `transition-followup.xlsx` (SHA-256 `70e277f224b1a22d8918ab18a9d55e5f5ed0cc185787f5ae6c5dcbdbfdbaccfa`), generated by `visual/transition_fixtures.py --set followup` in the stress harness at `74c43273`. All 52 formulas were measured on both sheets; none were unread or stale.

The updated rules were checked against the synthetic `transition-eval.xlsx` pair (fixture generator revision `2310f899`, workbook SHA-256 `3791f66406a699c082ca67c6622452ac0f96e5ee28b1c15c14d4560c2b7e06b2`). Excel for Mac 16.115.2 recalculated 1,028 formula pairs across 1,049 labelled rows per sheet; 255 formula results differed between transition and control. The probe includes all six comparison operators over the operand matrix and the individual function forms above. [Microsoft's Lotus compatibility settings](https://support.microsoft.com/en-us/excel/advanced-options) also document the zero/one coercions and distinct database-criteria rules.

## Residuals and migration

- The selected public BIFF examples have 206 mismatched formula cells on transition-enabled sheets in four `.xls` workbooks. This counts the discrepancies on those sheets. It does not claim that the flag causes all 206. In `SCD-G1.XLS` and `OPEC2.XLS`, additions over text operands cache what reading the text as zero gives. The adapter cannot infer the setting from formulas or cached results. A future `craft-xls` API should expose `Sheet::transition_evaluation: bool` (default false), populated from `fAltExprEval` in the [WsBool record](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xls/ccbd73f9-ff1d-4069-be31-13d16c074ec4). The GridCraft adapter can then copy it to the worksheet model and keep it on XLSX export.
- XLSB has the same flag (`fAltExprEval` in [`BrtWsProp`](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xlsb/4f648423-1efd-489c-90eb-ca410b8c5a12)). The `craft-xlsx` package reader owns this record and would need to pass the flag through to GridCraft. No selected XLSB mismatch was attributed to this flag.
- Transition mode does not change the result type of logical expressions. The synthetic comparison results are Booleans, even when the operands are compared numerically.
- Two legacy formulas in one workbook cache `N` of an entirely blank cross-sheet row range as zero. Taking the first cell explains this, but so do other ways of handling blank input. `N` already takes the first cell of a reference in the function evaluator, and the legacy XLSX importer has a separate implicit-intersection rule. That rule should stay as it is until there is more evidence, especially for nonblank ranges and computed arrays.
- Fifteen public query workbooks use manual calc and cache a bare legacy `Concat` call over a range of row numbers as `#VALUE!`. These caches do not establish how modern [CONCAT](https://support.microsoft.com/en-us/office/concat-function-9b1a9a3f-94ff-41af-9736-694cbd6b4ca2) behaves, since it accepts ranges. The missing future-function prefix, the old formulas and manual calc all point to legacy function resolution or stale caches. Text-function discrepancies that depend on these cells should not drive changes to `CONCAT`, `LEFT`, `LEN`, `TRIM` or `&`.
